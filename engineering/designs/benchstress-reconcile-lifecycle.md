# Benchstress reconcile lifecycle

## Objective

Replace Benchstress's old all-or-nothing create (one POST that persisted
config and dispatched `BenchstressWorkflow` in the same request) with a
step-wise, resumable setup that mirrors the reconcile pattern already used
by Fleet/Kafka/Flink: persist desired state first, dispatch later through a
single reconcile boundary. This lets the create wizard collect Placement
Configuration and Advanced Configuration across two steps, survive a
refresh or a browser close mid-setup, and guarantees at most one
`BenchstressWorkflow` run per desired-state generation.

## In scope

- `ClusterBenchmark` gains `configuration_state` (incomplete/valid/invalid),
  `desired_lifecycle`, `generation`, `observed_generation`, and
  `reconciliation_state`, plus a `BenchmarkReconcileOperation` outbox model
  (one row per create/delete attempt, unique on
  `(benchmark, generation, kind, idempotency_key)`).
- `topic` and `scenario_name` become optional at save time (`blank=True,
  default=""`) so the wizard can persist a partial draft after step one.
- `BenchmarkReconcileService.reconcile()` (`core/services/benchmark_reconcile.py`)
  is the sole place a benchmark's persisted desired state turns into a
  Temporal dispatch. It decides + persists an Operation inside one locked
  transaction; it never dispatches itself.
- `core/services/benchmark_reconcile_dispatch.py` performs the actual
  post-commit dispatch (`dispatch_pending_operation`), cancellation of a
  superseded active operation, and the manual stale-operation sweep
  (`sweep_stale_operations`).
- `POST .../kafka/{kafka_id}/benchmarks/{identifier}/reconcile/` and
  `POST .../kafka/{kafka_id}/benchmarks/reconcile-sweep/`
  (`core/views/kafka/benchmark_reconcile.py`) are the only HTTP entry points
  that can trigger a dispatch; `DELETE .../benchmarks/{id}/` routes through
  the same `reconcile()` call for teardown.
- A benchmark's config is immutable once reconciled — there is no Update
  workflow or "update" `kind`, only `create`/`delete`, unlike Flink which
  has a real Update workflow.
- Frontend: `BenchStress.js` step-wise wizard, `hooks/benchstress.js` gains
  `reconcileBenchmark`, `updateBenchmark`, `cancelBenchmarkSetup`.
- Migration `0173` backfills pre-existing rows: every row with both
  `placement_config` and `advanced_config` set is marked
  `configuration_state="valid"`; only rows additionally `status="Completed"`
  with a real `workflow_id` are marked `observed_generation=1,
  reconciliation_state="succeeded"` (everything else is left
  `never_reconciled`, since there's no real `BenchmarkReconcileOperation`
  audit row backing a pre-migration dispatch to hang a terminal state off
  of).

## Out of scope

- A Benchmark Update workflow — config is immutable once reconciled.
- CLI/MCP exposure of the reconcile/reconcile-sweep endpoints. Precedent:
  Flink/Kafka/Kafka Connect/Kafka Replicator/Virtual Kafka Cluster reconcile
  endpoints have SDK clients (generated by CI) but no CLI subcommands either
  — only `fleet reconcile` has one. Benchstress follows the same precedent.
- An automatic/cron sweep — `reconcile-sweep` is manually triggered only,
  mirroring `FlinkReconcileSweepView`.

## Approach

1. Add the five lifecycle fields to `ClusterBenchmark` and the
   `BenchmarkReconcileOperation` outbox model (migration `0173`).
2. `BenchmarkReconcileService.reconcile()`: lock the benchmark row, check
   completeness (`topic`, `scenario_name`, `placement_config`,
   `advanced_config` all present), resolve `kind` (create/delete), and
   short-circuit as unchanged when `observed_generation == generation` and
   `reconciliation_state == "succeeded"`. Otherwise create/reuse a
   `BenchmarkReconcileOperation` row scoped by the caller's
   `Idempotency-Key`.
3. `benchmark_reconcile_dispatch.py` dispatches through
   `CommandDispatchService` (never a raw Temporal client), using
   `BenchmarkReconcileWorkflowInput` (`core/command_dispatch.py`) —
   deliberately `extra="allow"` because `BenchstressWorkflow.run()` only
   reads `.action` and derives org/kafka/benchmark IDs by splitting its own
   workflow ID, not from workflow input.
4. `BenchmarkReconcileView.post()` requires `Idempotency-Key` (400 if
   absent) and an integer `generation` in the body, calls `reconcile()`,
   and — only when `should_dispatch` is True — attempts the dispatch
   synchronously before responding, so the caller sees the resolved state
   rather than a stale "queued" claim.
5. Frontend wizard persists Placement Configuration then Advanced
   Configuration via `updateBenchmark`, then calls `reconcileBenchmark`;
   `cancelBenchmarkSetup` discards an incomplete draft.
