# Gateway certificates: storage, serving and trust

Retrospective spec (written after implementation, PR #1393) for review.
Builds on `tailscale-tunnel-and-gateway-tls.md` (onboarding, the tailnet certificate).

## Objective

Every certificate Streamtime's gateway serves lives in GlobalConfiguration, can be
generated or uploaded from Settings, is served by Kong without files, and every
client of the gateway trusts what it serves.

## Design

### Storage (GlobalConfiguration)

- Built-in certificate (`*.streamtime.local`, the API host): `gateway_builtin_cert_pem`,
  `_key_pem`, `_sans`, `_expires_at`, `_source` (`bundled` | `generated` | `uploaded`).
  Seeded at startup from the mounted bundled files, else generated.
- A generated built-in certificate also covers the Streamtime API host when
  `BUILTIN_SANS` do not (`builtin_generated_sans`; `localhost` on single-node).
- The gateway (tailnet / bring-your-own) certificate: existing `gateway_tls_*` keys.

### API (typed settings, no verb endpoints)

- `GET|PUT /organizations/{org}/settings/builtin-certificate/` and
  `.../settings/gateway-certificate/`; validation is `PUT ?dry_run=true`.
- Internal (Kong, `X-Streamtime-Internal-Key`, JWT-exempt):
  `GET /organizations/{org}/gateway-certificates/` returns every served certificate with
  its key; the built-in one is the default.

### Serving (Kong)

- `kong-authz-proxy` `certificate` phase (`tls.lua`): picks the certificate for the
  handshake's SNI from the cached list (`kong.cache`, `cache_ttl` 300 s,
  `stale_ttl` 3600 s), falls back to the default. No certificates in kong.yml or files.
- A save drops the cache entry (`DELETE /cache/streamtime-tls:certificates`).

### Trust distribution (`gateway_trust_bundle()`: every served certificate)

- Kafka OAuth clients: `tls_trusted_cert` on the built-in OIDC provider.
- Tailscale fleets: agent chart `gatewayCA` always set to the bundle (was only with the
  registry on the tailnet); operator `gatewayCA`; egress backend `caCert` for Envoy's
  JWKS fetch.
- Agent → orchestrator (Temporal over the gateway): verifies against the bundle
  (`orchestrator_tls_ca_bundle` → chart `streamtime.orchestrator.tls.caBundle`, passed as a
  values document) when a served certificate covers the orchestrator server name;
  otherwise skip-verify with a warning. The install fails fast if asked to verify
  without a bundle.

### Console through Kong

- Compose: Kong route `console` (`console.streamtime.local`) → Vite dev server over
  plain HTTP (`HTTPS=false`, no key mounted); URL `https://console.streamtime.local:8443`
  (Kong `frontend_base_url`, `VITE_REDIRECT_URL`, Keycloak client URLs, CORS); hot reload
  over `wss` on 8443 (`VITE_HMR_CLIENT_PORT`); route-level OpenTelemetry
  `sampling_rate: 0`.
- Single-node: public address `https://localhost:8443` (`FLEETMANAGER_EXTERNAL_URL`,
  frontend env, Kong auth handler), 8443 published; Kong already routed `/` to nginx.
- Kong proxy buffers 16 KB (`KONG_NGINX_PROXY_PROXY_BUFFER_SIZE`): the console's
  Content-Security-Policy is ~5.5 KB; the 4 KB default returned 502.

## Out of scope (follow-ups)

- A Streamtime CA in GlobalConfiguration so rotating the generated certificate needs no
  fleet change (today fleets keep install-time copies; agent upgrades do not refresh
  them).
- Streamtime's own containers trust the bundled file, not GlobalConfiguration.
- Uploaded CA-issued certificates: the bundle carries the leaf only (Envoy needs the
  issuer as anchor).
- `docker-compose-public.yaml` and `kong.trial.yaml` still point at `http://localhost:3000`.

## API contract impact

New `settings/builtin-certificate/`, `settings/gateway-certificate/`,
`gateway-certificates/`; removed `gateway-tls/` verbs (see the tunnel plan's
Deviations). SDK snapshot regenerated by CI.

## Tests

- Backend: `test_gateway_tls` (incl. generated SANs), `test_builtin_oidc_trust`,
  `test_orchestrator_connection` (agent verification), `test_tailscale_fleet`
  (`gatewayCA` bundle), `test_network_views`.
- Gateway: `04-tls_spec.lua`.
- Orchestrator: install workflow passes the CA bundle as a values document and refuses
  verification without one.
- Live: bundle verifies `orchestrator.streamtime.local` locally and over the tailnet; a
  fresh agent runs with `TLS_SKIP_VERIFY=false`; console page, modules, deep links and
  HMR WebSocket through Kong; served certificate equals the stored built-in one.

## Deviations

- **2026-10-07 — HSTS follows an administrator's choice, not static config.**
  `kong.yml`, `kong.singlenode.yaml` and `kong.trial.yaml` sent
  `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` on the
  API routes. After a certificate was re-issued from the Streamtime CA, browsers
  that had pinned HTTPS refused it with no way to continue. Now generating or
  uploading a certificate takes `hsts_enabled` (off by default, stored as
  `gateway_hsts_enabled`, reset by `/setup/reset/`); the backend passes `hsts`
  with the served certificate, and `kong-authz-proxy` (`tls.hsts`, header phase)
  sends `max-age=<tls.hsts_max_age, default 31536000>; includeSubDomains` when on
  and `max-age=0` when off, which clears earlier pins in browsers that can still
  connect. `preload` is gone (never submitted). Helm's
  `secure-response-headers` plugin is unchanged: its certificates come from
  cert-manager.
