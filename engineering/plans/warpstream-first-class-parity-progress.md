- **Wildcard-cert finding (requirement 6):**
  - **Auto-TLS mode: assumption holds, confirmed by construction.** `_populate_cert_manager_auto_tls()` is fully workload-agnostic (only sets `certManager.namespace`/`clusterIssuerName`/`acmeEmail` — it has no opinion on SAN shape). The actual SAN shape comes entirely from the chart template `external-certificate.yaml` (Session 2), which hardcodes `commonName: "*.{domain}"` / `dnsNames: ["*.{domain}", "{domain}"]` — identical to Strimzi's own template. Since `AUTO_CERT_DNS_PROVIDERS` only admits DNS-01-capable providers (Route53/Cloudflare/STDNS — GoDaddy explicitly rejected via `GODADDY_AUTO_CERT_ERROR`), which support wildcard SAN issuance by construction, the wildcard cert always covers `{ns}-schema-registry.{domain}`.
  - **BYO PEM mode: assumption does NOT provably hold.** Traced `BaseDomain` creation's cert/domain validation to `core/views/shared/utils.py:55` `is_domain_valid_for_cert()` — it only checks `domain == common_name or domain in san_names`, i.e. the apex domain string appears *somewhere* in the cert's CN/SAN. It never requires a wildcard. An operator could legitimately upload a BYO PEM cert whose SAN is just `["kafka.example.com"]` (no `*.`) and it would pass `BaseDomain` creation validation, then silently fail TLS at the per-broker/bootstrap/SR Gateway hostnames.

### Post-Session 8d — `/code-review` finding: S3 bucket ownership not retry-stable across Temporal activity retries (2026-09-09)

- **Confirmed and fixed:** `warpstream_ensure_s3_bucket`'s `created` flag (`workflows/warpstream.py`) was derived from local, attempt-scoped Python state (did *this* attempt's own `create_bucket()` call run), not a durable property of the bucket itself. The activity's caller uses `RetryPolicy(maximum_attempts=10)` with no `heartbeat_timeout` — real Temporal-level retries are enabled. Sequence: attempt 1's `create_bucket()` succeeds in AWS, but a worker crash/network blip before Temporal durably records that attempt's success triggers a retry; attempt 2's `head_bucket` now finds the bucket (attempt 1 really did create it) and takes the "already exists; reusing" branch, returning `created: False`. DELETE (`warpstream.py:1379-1397`) gates bucket cleanup purely on this flag — a lost `created=True` means a Fleet-Manager-created bucket is silently orphaned forever, a genuine permanent resource leak, not cosmetic.
- **Fix applied — durable marker object, not a pre-write to backend state:** writing `created=true` to backend/workflow state before the activity could be interrupted doesn't actually solve it (that write is itself just another interruptible network call). Added `_S3_OWNERSHIP_MARKER_KEY = ".fleet-manager-owned"`: on the create path, `s3.put_object(..., Key=_S3_OWNERSHIP_MARKER_KEY)` immediately after `s3.create_bucket()` succeeds; on the "bucket already exists" path, `s3.head_object(..., Key=_S3_OWNERSHIP_MARKER_KEY)` determines `created` instead of hardcoding `False`. Chose a marker **object** over bucket **tagging** deliberately — tagging would need a new IAM permission (`s3:PutBucketTagging`/`s3:GetBucketTagging`) on the user's own inline AWS credentials that isn't currently documented as required; a marker object only needs `s3:PutObject`/`s3:GetObject`, which the credentials must already grant since WarpStream itself writes/reads real data into this same bucket.
- **`warpstream_delete_s3_bucket` confirmed to need no changes** — re-read it explicitly rather than assuming: it already lists and deletes every object in the bucket before `delete_bucket` (`workflows/warpstream.py:376-383`), so the marker object is cleaned up automatically as part of existing bucket-emptying logic. Stating this explicitly rather than leaving it implied, per this session's own instruction.
- **Residual limitation, disclosed honestly, not claimed as fully closed:** this narrows the race window from "the entire activity round-trip to Temporal" down to the single gap between `create_bucket()` returning and `put_object()` completing — not fully eliminated. ### Ad hoc — shared `kong-gateway` Gateway stuck on stale TLS cert ref, blocking Grafana + Kafka Metrics UI on `secondary-tarantula` (real AWS/EKS), root-caused and live-fixed (2026-09-09)

- **Symptom, two independent surfaces:** (1) Grafana at `shared-secondary-tarantula.iymaan.fleet-manager.platformatory.io` returned `DNS_PROBE_FINISHED_NXDOMAIN` in-browser; (2) the Streamtime UI's Kafka Metrics panel for `coherent-porpoise` showed *"Kafka metrics were returned with query errors for this time range, so there is no usable time-series data to plot"* — every one of 25 panels came back `status: "error"`, including panels querying metrics independently confirmed present and populated (`warpstream_agent_control_plane_operation_counter`), ruling out a metric-name cause.
- **Root cause, confirmed via live `kubectl` inspection, not guessed:** the shared `kong-gateway` Gateway object (namespace `secondary-tarantula`, created by the `fleet-manager-infra-shared` Helm install at `16:57:14Z`) has an `https` listener whose TLS `certificateRef` points at `secondary-tarantula/tls-kafka-external` — the same Secret populated by cert-manager's `external-kafka-cert` Certificate. At the moment the Gateway was first reconciled, that Secret didn't exist yet (this was itself downstream of the stale orphaned Route53 `_acme-challenge` TXT record fixed earlier this session — see the fleet-selection/cert-manager entries above). Kong's gateway-operator set the listener's `ResolvedRefs` condition to `False` (`InvalidCertificateRef`, *"Referenced secret secondary-tarantula/tls-kafka-external does not exist"*) at `16:57:42Z` — **and never re-checked it**, even 23+ minutes after the Secret was actually created once the Certificate issued successfully. Because the listener never reached `Programmed: True`, every `HTTPRoute` parented to it stayed `Accepted: False, reason: NoMatchingParent` — confirmed **6 routes** affected: `grafana-httproute`, `prometheus-httproute`, `alertmanager-httproute`, `loki-httproute`, `otel-httproute` (all namespace `monitoring`), `opencost-httproute` (namespace `opencost`). Since `prometheus-httproute` was one of them, the local dev backend's proxy call to the fleet's Prometheus (`.../fleet/secondary-tarantula/endpoints/metrics/...`) had nothing to route to, which is what produced the Kafka Metrics UI's uniform per-panel `"status": "error"`.
- **Fix applied, user-approved:** `kubectl annotate gateway kong-gateway -n secondary-tarantula reconcile.trigger=<timestamp> --overwrite` — a no-op annotation patch, just enough to trigger a fresh reconcile without touching spec. **Effective immediately**: listener flipped to `ResolvedRefs: True` (`"Listeners' references are accepted."`), `Programmed: True` in the same reconcile pass. All 6 `HTTPRoute`s flipped to `Accepted: True, Programmed: True (ConfiguredInGateway)` within the same check. `external-dns`'s next sync cycle (60s later) picked up the newly-Accepted routes and created the missing `A`/`AAAA`/TXT records for `shared-secondary-tarantula.iymaan.fleet-manager.platformatory.io` in Route53 — confirmed via a direct query against the authoritative nameserver (real ELB IPs returned) and via `curl --resolve` against Grafana's login page (`302`, normal Grafana behavior).
- **Residual, separate, self-resolving issue found while re-verifying — not a bug in anything we touched:** even after the DNS record existed at Route53's authoritative source, both this session's sandbox host and the docker-compose `fleet-manager-gateway` (Kong) container — which forwards through the host's `127.0.0.53` systemd-resolved via Docker's embedded DNS (`127.0.0.11`) — kept returning `NXDOMAIN` for several minutes past record creation. Restarting the `fleet-manager-gateway` container did not clear it (fresh worker PIDs, same failure), which rules out an in-process Kong DNS cache and points at the host's own recursive resolver still holding a negative-cached/not-yet-propagated result, independent of Kong or Fleet Manager config. `dig` directly against the Route53 authoritative nameserver resolved correctly throughout. **Not something to fix in the codebase** — ordinary DNS propagation lag through this environment's resolver chain, expected to clear on its own; flagged rather than worked around by editing Kong's `KONG_DNS_RESOLVER` (which would be a separate, out-of-scope infra change beyond tonight's approved single reconcile action).
- **Is this a one-off or a general race? — evaluated honestly, not defended as one-off.** The proximate trigger tonight (a long-stuck cert issuance caused by the stale Route53 record) made the window unusually long (~47 minutes) and thus visible, but the **underlying gap is structural, not tied to tonight's specific delay**: `fleet-manager-infra-shared`'s Helm release creates the `Gateway` (referencing the TLS secret by name) and the `Certificate` (which populates that same secret) in the same install, with no ordering between them, and DNS-01 ACME issuance inherently takes at least tens of seconds even in the best case (challenge propagation + validation round-trip) — so the Gateway's very first reconcile will essentially always race a not-yet-existent Secret on every new fleet using `auto_create_certificates=True`. Whether this self-heals invisibly (some other unrelated watch event happens to re-trigger a Gateway reconcile before anyone hits the routes) or gets stuck exactly like tonight depends on incidental timing/traffic on the gateway-operator's controller, not on anything Fleet Manager controls. **Flagging as a new open item, not fixed here**: `fleet-manager-infra-shared`'s Helm chart (or the orchestrator's `BootstrapFleetClusterWorkflow`) should either (a) wait for `external-kafka-cert`'s Secret to exist before/independently of installing the Gateway, or (b) have the orchestrator poll the Gateway's listener `ResolvedRefs`/`Programmed` status after cert issuance completes and force a reconcile (the same one-line `kubectl annotate` patch used here) as a normal post-cert-issuance step, rather than relying on incidental re-reconciliation. Real fix belongs to whichever session next touches `fleet-manager-infra-shared` or the AWS/BYOK bootstrap workflow — not attempted here, scope was live remediation only, per explicit user approval for this one action.
